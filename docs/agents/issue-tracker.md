# Issue tracker: GitHub

Issues and specs live in GitHub Issues in `SphericalKat/opencoode`. Use the `gh` CLI from this clone.

## Operations

- Verify the target: `gh repo view --json nameWithOwner`.
- Create: `gh issue create --title "..." --body-file <path>`.
- Read: `gh issue view <number> --json number,title,body,labels,comments,author,createdAt,updatedAt`.
- List: `gh issue list --state open --limit 100 --json number,title,labels,author,createdAt,updatedAt`. Paginate with `gh api` when the result limit is reached.
- Comment: `gh issue comment <number> --body-file <path>`.
- Apply or remove labels: `gh issue edit <number> --add-label "..." --remove-label "..."`.
- Close: post the explanation first, then `gh issue close <number>`. Post comments separately even when the issue is already closed.

Use temporary files for multiline bodies. Before creating an issue, verify that the target is this repository.

## Relationships

Use native GitHub sub-issues and issue dependencies where available. Otherwise, put `Part of #<parent>` and `Blocked by: #<number>` in the child body and link the child from the parent. A ticket is unblocked when all its blockers are closed.

## Pull requests as a triage surface

**PRs as a request surface: no.**

GitHub shares issue and PR numbers. For an explicitly named number, resolve its type with `gh api repos/SphericalKat/opencoode/issues/<number>`; the `pull_request` field identifies a PR.

## Skill conventions

“Publish to the issue tracker” means create a GitHub issue. “Fetch the relevant ticket” means read the issue, including comments.

Every comment or issue posted during triage must start with:

> _This was generated by AI during triage._
